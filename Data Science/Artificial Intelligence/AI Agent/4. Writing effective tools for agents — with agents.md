# 写工具

1. 构建工具原型

2. 创建全面测评并使用测评评估工具

&emsp;&emsp;用简单的agentic loops，while循环包LLM API call + 工具调用，一次循环就是一次测评任务

输出应包括：在调用工具前输出回复、推理、反馈，工具调用次数，token消耗，工具错误，任务和工具调用实践

3. 分析结果，借用agent本身的帮助迭代

主要看模型的推理和反馈过程，和模型调用工具的参数。注意模型推理和反馈中**没说的东西**常常比说了的东西更重要，模型的意图和它说的话并不总是一致：[www.anthropic.com](https://www.anthropic.com/research/tracing-thoughts-language-model)

**个人思考**：没说的东西才是模型真正卡住的地方。意图和话不一致，要理解这一点得看链接的另一篇文章。

# 写工具的原则

* 搞清楚应该实现和不该实现的工具

schedule event这个工具就要好于list users, list events和create\_event。search\_logs好于read\_logs。get customer context好于get customer by id, list transactions和list notes

**个人思考：**应该是说要把模型拟人化对待（工具要对agent ergonomic）。模型对工具的理解应该是基于任务结构而不是系统的数据结构，也不要给模型一大堆东西让模型去做筛选，工具给到模型的就应该是尽可能精简的结果以节省上下文。

* 给工具一个命名空间以明确功能边界，方法是使用相同前缀：asana\_projects*\_*search, asana\_users*\_*search\)

&emsp;&emsp;作者发现使用前缀还是后缀作为命名空间区别还不小，因此建议根据我们自己的具体的评测结果来判断。

* 工具应该返回有意义的信息

上下文相关性大于灵活性，扔掉底层技术标识符（uuid，mime\_type，256px\_image\_url），而用name, image\_url, file\_type

**个人思考：**灵活性的意思应该是指全面性，也就是说提供过多信息，希望能覆盖所有可能用法

作者发现仅仅是把uuid重新解析成有意义的语言，甚至是0\-indexed的id序列，也能显著提升Claude精度、降低幻觉

**那又需要工具灵活性咋办？**暴露一个枚举变量叫response\_format，模型决定传入"detailed"还是"concise"。甚至可以向GraphQL学习，模型直接指定想要什么信息。

* 优化工具回复的数量以提高token效率

使用分页、范围选择、过滤、截断等参数手段

Claude Code限制工具回复在25000tokens以内，工具的回复长度不该随时间增长

鼓励agent做多次小范围聚焦搜索，而非单次大范围搜索

tool的错误回复可以提供具体、可操作的改进建议（甚至例子），而不只是隐晦的报错码和追踪路径

* 工具descriptions和specs的提示词工程

&emsp;&emsp;输入参数命名不可有歧义，user\_id好过user

&emsp;&emsp;隐藏信息，如特殊请求格式，小众词汇定义，底层资源关系
