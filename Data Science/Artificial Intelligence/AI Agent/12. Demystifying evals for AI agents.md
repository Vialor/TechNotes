我们需要一个评测系统（在agent的生命周期中，这件事的**价值会逐渐加强**），因为：

    1. 避免陷入被动循环：在生产中才发现问题，**修好一个问题又创造了别的问题**

    2. 在**影响到用户**之前，使问题和行为变化可视化

    3. **明确AI预期行为**，工程师很可能对同一个edge case有分歧

    4. 更快**适应新的模型**，当新模型出来时能快速测试其能力，并调整提示词

评测应该尽早搞，因为：

    1. the 80/20 approach：早期的小投入就能产生大收益，后面agent更成熟，评测检查到细节会更难

    2. 一开始产品需求很自然就会变成测试用例，时间久了，我们就会需要从一个上线系统中逆向工程出一个agent的成功标准了

但是，agent的自治、智能和灵活既是它的优点，也使他们**难以被评测**。

# Agent测评结构

**Single\-turn evaluations**很直观: a prompt, a response, and grading logic。AI能力进步以后，**multi\-turn evaluations**也越来越常见。

**Agent evaluations：**（很困难。因为错误会滚雪球；模型也可能发现意外捷径而被误判为错误，Opus 4.5找到了政策漏洞来帮客户订飞机票，却被评测系统判错）

* **task **\(a.k.a **problem** or **test case**\)：有明确输入和成功标准的单个测试

* **evaluation suite**：一套tasks，用来测试特定能力和行为

* **trial**：对task的一次尝试（多次trail以减轻随机性、获取更一致的结果）

* **grader**：评价agent某些方面表现的逻辑，一个task可有多个grader，每个grader含多个断言** assertions \(checks\)**

* **transcript **\(**trace **or** trajectory**\)：一次trail的完整记录，包括输出，tool calls, 推理，中间结果和其他交互

* **outcome**：trail结束时环境的最终状态（功能是否实现了？不只是模型说了什么）

* **evaluation harness**：端到端跑测试的基建，提供指令和工具。并发运行任务，记录步骤，评价结果，聚合结果。

* **agent harness **\(or **scaffold**\)：让模型表现得像一个agent的系统，它处理输入，编排tool calls并返回结果。当我们测评一个agent的时候是测评模型和harness一起的工作。

# Agent测评方法

## 三类Graders

**Code\-based graders**

|**Methods**|**Strengths**|**Weaknesses**|
|---|---|---|
|• String match checks \(exact, regex, fuzzy, etc.\) • Binary tests \(fail\-to\-pass, pass\-to\-pass\) • Static analysis \(lint, type, security\) • Outcome verification • Tool calls verification \(tools used, parameters\) • Transcript analysis \(turns taken, token usage\)|• Fast • Cheap • Objective • Reproducible • Easy to debug • Verify specific conditions|• Brittle to valid variations that don’t match expected patterns exactly • Lacking in nuance • Limited for evaluating some more subjective tasks|

**Model\-based graders**

|**Methods**|**Strengths**|**Weaknesses**|
|---|---|---|
|Rubric\-based scoringNatural language assertionsPairwise comparisonReference\-based evaluationMulti\-judge consensus|FlexibleScalableCaptures nuanceHandles open\-ended tasksHandles freeform output|Non\-deterministicMore expensive than codeRequires calibration with human graders for accuracy|

**Human graders**

|**Methods**|**Strengths**|**Weaknesses**|
|---|---|---|
|SME reviewCrowdsourced judgmentSpot\-check samplingA/B testingInter\-annotator agreement|Gold standard qualityMatches expert user judgmentUsed to calibrate model\-based graders|ExpensiveSlowOften requires access to human experts at scale|

## 能力评估 vs 回归评估

**Capability or “quality” evals** 要回答“Agent能做什么”，一开始通过率很低，后面应该逐渐提升

**Regression evals** 要回答“Agent还能处理它以前能干的任务吗？”，通过率应该接近100%，避免跷跷板问题，解决一个问题导致以前的问题又出现了

**当能力评估达到高通过率后，将其"毕业"为回归评估。**  

## 各类Agent的测评示例

### **Coding agents**

* 验证正确性（**确定性测试**，如单元测试）

* 评估代码质量（**LLM rubric**，静态分析）

* 常用benchmark：SWE\-bench Verified、Terminal\-Bench

```yaml
task:
  id: "fix-auth-bypass_1"
  desc: "Fix authentication bypass when password field is empty and ..."
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
    - type: tool_calls
      required:
        - {tool: read_file, params: {path: "src/auth/*"}}
        - {tool: edit_file}
        - {tool: run_tests}
  tracked_metrics:
    - type: transcript
      metrics:
        - n_turns
        - n_toolcalls
        - n_total_tokens
    - type: latency
      metrics:
        - time_to_first_token
        - output_tokens_per_sec
        - time_to_last_token
```

### **Conversational agents**

* 检查可验证的最终状态，ticket解决了吗（**state check**）

* 是否在10轮内解决问题（**transcript constraint**）

* 语气是否得体（**LLM rubric**：如同理心、解释清晰度）

* **需要第二个 LLM 模拟用户**来和被测agent交互

* 可用benchmark：𝜏\-Bench 及后继者 τ2\-Bench

```yaml
graders:
  - type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
      - "Agent showed empathy for customer's frustration"
      - "Resolution was clearly explained"
      - "Agent's response grounded in fetch_policy tool results"
  - type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}
      - {tool: send_confirmation}
  - type: transcript
    max_turns: 10
tracked_metrics:
  - type: transcript
    metrics:
      - n_turns
      - n_toolcalls
      - n_total_tokens
  - type: latency
    metrics:
      - time_to_first_token
      - output_tokens_per_sec
      - time_to_last_token
```

### **Research agents**

* **Groundeness**：agent的推论是否被agent取回的信息支持

* **Source quality**：调查源是否权威

* **Coverage**：答案必须包含关键事实

* **Coherence &amp; Completeness**

* LLM为基础的rubric需频繁人工校准

* 一个benchmarlk：BrowseComp，agent能否“海里寻针”？

### Computer use agents

* 在真实或沙盒环境中运行，使用GUI而非代码或API

* **两种交互思路：基于DOM或截图**，前者更消耗token，但执行快且精准。后者处理慢，但对视觉理解任务更好。前者适合wikipedia总结，后者适合amazon购物。

## 应对测评agent时的非决定论性

重点变成了测一种频率，这样理解：

pass@k：对全部任务来说，“k trails中至少一次成功”的比例。用于"只要有一个成功就行"的开发工具

pass^k：对全部任务来说，“k trails全部成功”的比例。用于需要每次都可靠且一致的面向客户的系统

k越大，pass@k越接近1，pass^k越接近0

# Agent测评建立

Evalutation suite 开发：1\-4

Harness 开发：5\-6

维护测评系统：7\-9

1. **尽早开始**，20\-50 个简单的真实失败案例就是很好的起点

2. 将我们开发中已经在手动检查和用户生产中反馈的失败转化成测试用例

3. 写**无歧义的任务**：两个领域专家应该能独立在此任务中得到同样的结论

4. 构建**均衡的问题集**：既有应该发生的，也有不应该发生的

5. 为eval harness准备**稳定、干净的运行环境**

6. 设计graders：优先用确定性评分器，当需要额外灵活性时使用LLM评分器，审慎使用人工校验

    1. **不要严格检查工具调用顺序**，太严格了，且惩罚创新

    2. 对于多步骤任务，给**步骤分**

    3. LLM评分器需人工仔细校准；为了避免幻觉，始终**保留模型说不知道的权力**：unkown；系统成熟以后，人工介入会越来越少

    4. 即使很精深的团队也会面临**grader的错误配置，歧义和各种grader本身bug导致评分过低**

7. 定期阅读transcript确认评分是否公平，公平的意思是说确保**分低是agent导致的而非评测本身**

8. 监测能力评测饱和度 **Eval saturation**

**Eval saturation **是一种现象，描述的是agent解决了所有任务，而没有空间进步了，这里的核心教训是：

通过率接近100%时会变难，因为**剩下的都是长尾难题**

这使结果变得具有欺骗性，因为**真正的能力提升就在最后的小分**上

因此**分数表面意义是空洞的，读transcript和挖eval细节**才有意义

9. eval suite的长期健康需要**公开的贡献和维护**

作者实践最有效的方法是创建**专门的测评团队负责核心基建，领域专家和产品团队贡献评测任务并自己跑测试**

**产品团队应该日常维护迭代测评**，定义测评任务是最好的**压力测试产品需求是否清晰**的最好办法——eval\-driven development

开发者**不要闭门造车，最接近需求的人才最了解成功的定义**，应鼓励他们也借助Claude Code提PR

# eval结合其它方法以整体理解agent

**Agent开发的全周期：**

**自动化评测**在上线前和 CI/CD 场景里尤其有用：它会在 agent 的每次变更和每次模型升级时运行，作为防止质量问题的第一道防线。

上线后，则由**生产监控**接手，用来发现数据分布漂移以及现实环境中未曾预料到的失败。

等你有了足够流量之后，**A/B 测试**可以用来验证重大改动的效果。

**用户反馈和transcript审查**则是持续进行的补充手段，用来填补其他方法覆盖不到的空白：要持续分流和处理反馈，每周抽样阅读对话记录，并在需要时进一步深挖。

至于**系统性的人类研究**，则应当留给两类场景：一类是校准 LLM grader，另一类是评估那些带有主观性的输出，在这些情况下，人类共识可以作为参考标准。

# 碎片知识

**dogfooding**：在开发中使用交付给客户的工具，这个动作利于我们开发、也有利于以客户视角发现产品问题

take **the 80/20 approach** in the beginning：指的是帕累托法则，先用 20% 的投入，拿到 80% 的价值

# 个人思考

本文切中了很多我们开发时的大小痛点。这里最主要的教训是：测评工作不是agent开发工作之后的锦上添花，而是agent开发工作的基石。有了测评，我们才能理解方向和问题是什么。

AI相比传统软件工程的优势在于可以处理非决定论的问题，这对测评提出了新的需求。我们需要一个决定论或者近似决定论上的评估系统，来应对这个非决定论的系统。我说“近似决定论”的意思是1. 统计上样本足够多时，能呈现出确定的结果；2. 通过人工调整和多轮迭代，能够呈现出确定的结果。
