# 动机

**Context Rot:** 上下文窗口内token增多，模型准确回忆信息的能力就下降

因此：Context是一个有限且带有边际递减效应的资源，上下文工程是有意义的

## 底层

transformer架构里，每个token都要和其他所有token建立注意力。上下文太长，模型捕获这种n² 成对关系的能力就恶化。

模型注意力模式通常是通过较短的序列训练的，对长上下文比较陌生。

有些技巧，比如Position encoding interpolation，允许模型将长序列转化为训练时用的小上下文，代价是token位置理解恶化。后果是表现的逐渐而非断崖下降：模型仍能处理长上下文，但是信息提取和长距离推理相比短上下文会下降。

# 有效上下文的解析

System prompts要精简，并走一个平衡：不应该过于抽象模糊，或假设模型了解背景；也不应该描述过于复杂、僵硬、坚固但易碎的逻辑。

推荐开发方式是：先采用最少的必要prompt+最好的可得模型测一下表现，然后逐渐添加清晰指令和示例

工具写法见[Writing tools for AI agents – with AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents)，很多信息是重复这篇文章的

如果人类工程师不能肯定工具的使用场景，那就不该期望AI也能做到。

# Context retrieval and agentic search

推理前、基于向量相似度的检索的基础上现在更多地开始加入**即时上下文策略**：

&emsp;&emsp;工程开始使用轻量的标识符（文件路径、请求、网络连接等），并且使用工具动态地加载这些标识符后地数据（如head/tail/glob/grep命令）。

&emsp;&emsp;实现了 **Progressive disclosure：**允许Agent通过探索逐渐发现相关上下文

&emsp;&emsp;**个人思考：**即时上下文策略和原本检索的主要区别应该在于模型是否自主探索以获取信息

**推理前和推理时上下文策略结合：**

&emsp;&emsp;推理前上下文提供了更多人为指导以避免 agent 走错方向，并且运行时探索比提前处理好还是更慢的。

适合不那么动态的工作，并且作者预测随着模型能力增强，模型自主行动在设计中的权重会更大。因此，工程设计应该尽可能简洁够用就好。

**例子：**Claude Code使用混合模式 CLAUDE.md 文件就是大胆直接地放在上下文开头，元操作glob、grep可以即时读取环境和文件，这样就避免了索引过时和繁复语法树的问题。

**个人思考：**意思应该是说，如果不动态查询就需要静态构造，会出很多问题

## 长程任务上下文工程：三个主要技术

**Compaction**：把上下文快满了的对话总结一下，新开对话窗口上下文使用这个总结。

**例子：**Claude Code会保存架构决定，未解决bugs，实现细节，然后扔掉多余信息和工具输出。Agent带上压缩后的上下文和5个最近访问文件继续任务。

**prompt开发方式：**从复杂的agent轨迹开始，最大化信息召回率，然后逐渐迭代删去不必要信息。

**Structured note\-taking / Agentic memory：**模型规律性把笔记持久化到上下文以外的记忆系统，等待未来被重新载入上下文。

**Sub\-agent architectures：**特定的sub\-agent处理特定的任务，一个主agent在高纬度协调众sub\-agents。如此上下文内容得以被分割给不同agent。

**个人思考：**有没有可能存在用户自主维护的树状上下文系统。人解决问题的思路不是线性的，而是如同git那样的树状，也许辅助人工作的agent在对话时也应该采用这样上下文。用户把控解决问题的树状思路的同时也要维护树状的上下文，模型每次只读取从根到叶的一条路径作为上下文。
