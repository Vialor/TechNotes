Tool Search Tool，Programmatic Tool Calling，Tool Use Examples

# 方案

## Tool Search Tool

**Tool Search Tool：**一个搜索工具的工具

**动机：**Agents 根据当前任务，按需发现和加载工具定义，避免大量的工具定义占据上下文

**实现：**工具定义可以标记defer\_loading为True，这样的工具的定义一开始不会暴露给模型。当模型调用工具的时候，会先通过非模型的搜索算法 \(**regex\-based search, BM25\-based search, embeddings search，**Claude 生成 Python `re.search()` 风格的 regex 查询 或 自然语言查询\)，找到相关的工具定义。

Tool Search Tool 不会破坏 prompt caching，因为一开始并没有把所有工具都塞进 prompt，只有真正搜到、真正要用的工具，才会后加入上下文。系统提示词和核心工具定义还是可cache的。

**prompt cache: **模型推理引擎的功能之一，它把一段重复出现的输入前缀缓存起来，下次再遇到相同前缀时，就不用重新计算

**实践建议：**

* 使用时机：工具数量多，且节约上下文和工具选择准确性 > 延迟

* 添加系统提示指引，帮助Claude了解可用的工具：

```json
You have access to tools for Slack messaging, Google Drive file management, 
Jira ticket tracking, and GitHub repository operations. Use the tool search 
to find specific capabilities.
```

* 保存最常用的3\-5个工具处于加载状态，剩下的defer掉

**个人思考：**是不是也可以有Skill Search Tool，甚至Skill Search Skill？目前没有看到关于Skill metadata消耗大量上下文的解决办法。

## Programmatic Tool Calling PTC

**Programmatic Tool Calling**：允许Claude在代码执行环境中使用工具

**动机：**Agent应根据任务灵活选择代码执行还是推理。

    1. **Context pollution from intermediate results 中间结果污染上下文：**模型调用工具需要一次完整推理，不论是否有用，中间结果都会堆积在上下文中。

    2. **Inference overhead and manual synthesis 推理开销和手动综合：**代码天生适合编排逻辑，如循环、条件和数据转化；而模型需要推理工具调用的结果，来决定下一步怎么做，这个过程慢且易错。

**实现：**工具定义中可以标记为callable from code。模型写编排代码（orchestration code），然后在沙盒环境中执行代码，代码会调用工具。调用工具的过程不会进入模型上下文，只有最终结果会进入。

**实践建议：**

* 文档中输入输出格式要写清楚，便于模型写码

* 特别适合使用 PTC 的工具：

    * 可并行工具 \(独立操作\)

    * 重复执行也安全的工具 \(幂等操作）

## Tool Use Examples

**Tool Use Examples: **允许在工具定义中提供工具调用示例

**动机**：JSON Schema擅长定义结构类型，必须字段和可用枚举类型，但是不擅长描述使用范式：什么时候使用可选变量？那些组合是合理的？API期待的约定俗成的用法？ 让模型从例子中学习工具用法，而不只是schema定义。

&emsp;&emsp;**格式模糊 Format ambiguity：**"2024\-11\-06", "Nov 6, 2024" 还是 "2024\-11\-06T00:00:00Z"？

&emsp;&emsp;**嵌套结构 Nested structure usage：**嵌套对象里的子字段，什么时候该展开填写、什么时候该省略，以及各层字段该填到什么程度？

&emsp;&emsp;**变量关联 Parameter correlations：**比如有些可选字段只有当另一个字段存在的时候，才会存在

**实现：**Tool定义的input\_examples字段里面添加参数示例

**实践建议：**

* 简洁，一个工具1\-5个例子

* 覆盖最少参数版本，半完整版本和信息给全版本

* 用实际数据，不要用"string"，"value"这样的占位符

* 聚焦在模糊点上，只有正确用法在schema上不明显才加例子

**个人思考：**

● 有一次我们遇到太过复杂JSON使用逻辑，我还考虑过使用测试来规范用法，也就是把这种测试代码这种严谨的确定的内容作为上下文交给模型。但这个做法大概还是不如Tool Use Examples清晰，用代码定义用法对于模型来说可能过于晦涩了。如果模型能拿到测试的反馈，然后再优化，形成循环，类似Evaluator\-optimizer的结构，这也许是牺牲时间和资源来解决JSON过于复杂逻辑的一种办法。

● 当然如果1到5个例子还不能澄清用法歧义，也许schema应该重新设计和解耦。这个事情对于同事间对齐输入输出也是有帮助的。

# 思考

## Skill 状态机

我们最近遇到这样一个**工程问题**：需要写一个Skill A（我们无权修改使用Skill的平台本身的代码），该Skill可以在不改动Skill B核心逻辑的情况下，为它诊断问题、打补丁。

这个事情**有两个困难**：

1. 如何减少对Skill B核心逻辑的侵害，同时还能达成打补丁的需求。这个问题不在本文讨论范围之内。

2. 我们能使用的模型只有27B，模型语言功能尚可，逻辑能力十分差，基本上只能走直线；而问题诊断和修复是个很复杂的业务。因此整个迭代过程是通过用户和模型对话框交互完成的，毕竟我们不应该指望这么弱的模型一次就得到答案，我们也不应该指望用户一开始就能把信息完整正确地呈现。也就是说我们的系统需要适时停下来和用户对信息，并能在多轮对话中理解当前所处的流程阶段。

本文 Programmatic Tool Calling 的思想加深了我对语言模型的工程意义的理解，受此启发，我们的**基本思路是这样的**：

1. 把确定的、逻辑的问题交给代码（问题诊断流程的状态机），把模糊的、语言的问题交给模型（理解用户输入的本质）

2. 简化模型能接触到的信息，模型一次只看到一件事、只处理一件事，不管全局

**Skill里面指导模型具体Workflow是**：

1. 代码：获取当前状态机状态（从运行时文件读取）

2. 模型：解读用户上次的输入（如果有），将它归约到一个代码可理解的具体分类标签：如用户接受结果 USER\_ACCEPTED，用户拒绝结果 USER\_REFUSED

3. 代码：根据当前状态和2中的分类标签，调整状态机状态

4. 代码：输出当前状态给模型和用户，提供当前阶段的操作文本给模型（就是说具体执行文本一开始对模型是不可见的，由此避免模型受到其他阶段文本的干扰）

5. 模型：执行代码提供的文本，执行当前阶段的操作

## PTC 代码沉淀

我们以前在工程中不自觉地使用了 Programmatic Tool Calling 的思想。当时的场景是输入过长，不可以全部塞入上下文，因此希望靠模型写代码处理。这可以说是PTC除了本文提到的两处动机外的第三个动机了。

在当时的业务里，我们希望模型代码能留存沉淀下来，并且进行一定程度上的自动迭代。我认为这对于PTC来说是很常见的“接下来会有的需求”，毕竟每次都让模型写码是不稳定、也花时间的，尤其是对于那些流程固定、结构稳定又相对复杂的场景。沉淀的好处说完了，现在关键在于怎么理解“自动迭代”；这一部分，我目前还没有很好的实践经验。
