模型需要背景知识

**传统办法是 Retrieval\-Augmented Generation \(RAG\)**：从知识库拿相关信息、然后加到user prompt尾部的方法

**问题是：**传统 RAG 在把原始资料转成可检索表示时，**会丢掉一部分上下文信息**；而这些被丢掉的东西，往往恰恰会影响检索是否能把真正相关内容找回来。

本文**解决这个问题**：使用了 **Contextual Retrieval** 方法以及两个技巧，**Contextual Embeddings 和 Contextual BM25**

# 传统RAG工程实践

**基于Embedding的RAG流程：**

1. 分解知识库到小块文本（几百tokens）

2. 使用embedding model把小块文本变成向量embedding

3. 用向量数据库储存embeddings以便于通过语义相似度搜索

4. 基于语义搜索得到的chunks会给到模型user prompt尾部

**问题：**语义关系捕捉到了，但丢失关键的精确匹配

&emsp;&emsp;比如：用户问"Error code TS\-999"，embedding model会去找error code相关信息，而不能匹配确切的TS\-999

**办法：**更古老的手段 **BM25 Best Matching 25**，这是一个ranking函数，它通过词汇匹配找到最准确的词和短语。对独特标识符和技术词汇很有效。

BM25 基于一个概念：**TF\-IDF \(Term Frequency\-Inverse Document Frequency\)**，这个概念衡量一个单词，在整个文档集合内，对于一个文档有多重要。

词频：一个词在当前这篇文档里出现了多少次？逆文档频率：这个词在整个文档集合里常不常见？

BM25 改进了 TF\-IDF：将文档长度纳入考虑，并对词频应用了饱和函数

**综合Embedding和BM25的RAG流程：**

1. 分解知识库到小块文本（几百tokens）

2. 为小文本块建立TF\-IDF encodings和语义embeddings

3. 基于精确匹配用BM25找到一些最佳匹配语义块

4. 基于embedding语义相似度搜索找到一些最佳匹配语义块

5. 使用rank fusion技巧结合并去重3、4中的语义块

6. 将头k个语义块加到提示词中

这都很好，但是有个**大问题**：破坏了上下文，因为独立小语义块丢失了足够的上下文。Contextual Retrieval

# Contextual Retrieval

在每个文本块前添加解释性的上下文，然后再做embedding和BM25 index（Contextual Embeddings 和 Contextual BM25）

还存在其他办法，但不是本文要推销的：

[adding generic document summaries to chunks](https://aclanthology.org/W02-0405.pdf) （作者实验了，提升有限）

[hypothetical document embedding](https://arxiv.org/abs/2212.10496)（作者实验了，表现差）

[summary\-based indexing](https://www.llamaindex.ai/blog/a-new-document-summary-index-for-llm-powered-qa-systems-9a32ece2f9ec) （作者实验了，表现差）

**个人思考：**查了一下作者提到的其他方法分别是：

&emsp;&emsp;1. 给每个chunk生成**文档级别的摘要**再去做 embedding / 索引

2. 在查询阶段让模型根据问题“写一篇会回答这个问题的**假想文档**”，再把它编码成向量，用它去找真实语料中的邻近文档

3. 不是直接拿原始 chunk 建索引，而是先给文档或片段做**摘要**，再用摘要去建索引，检索时优先搜这些摘要

作者方法比较接近1、3，但粒度更细，并且强调是添加上下文信息本身，而不是摘要。

## 实现Contextual Retrieval

利用模型给每个chunk添加上下文：

```plaintext
<document> 
{{WHOLE_DOCUMENT}} 
</document> 
Here is the chunk we want to situate within the whole document 
<chunk> 
{{CHUNK_CONTENT}} 
</chunk> 
Please give a short succinct context to situate this chunk within the overall document for the purposes of improving search retrieval of the chunk. Answer only with the succinct context and nothing else. 
```

## Prompt Caching 削减成本

因此，不必每次推理都传入整个参考文本

生成带上下文的文本块的一次性成本：\$1.02 per million document tokens

# Reranking: 进一步提升性能

1. 初始检索拿到可能最相关的文本块 \(作者取了头150\)

2. 把这些文本块和用户的请求一起传给 reranking model

3. 用 reranking model 给每个文本块基于对提示词的相关性和重要性打分，然后选取top\-k个文本块 \(作者取了头20\)

4. 把头k个chunk传给模型作为上下文信息

**个人思考：**reranking的意义

    1. 作者说是基于对提示词的相关性和重要性打分的意思可能是：contextual retrieval找到的结果是语义和字面上接近的，目的是**提高召回率**。但是这些信息是不是**真的适合回答用户的问题，符合提示词的要求**？我们还需要深度理解、再筛选一下。就好像第一次筛选是基于简历，选出具有资质的候选者；第二次面试才是真正在思考，候选者是否真的匹配当前这个具体的岗位。

    2. 这是经典的**粗排+精排**的工程思路。作者提到rerank是昂贵的，虽然打分能够并行，但因为是**运行时的操作**，所以依然是昂贵的。因此放在精排。
