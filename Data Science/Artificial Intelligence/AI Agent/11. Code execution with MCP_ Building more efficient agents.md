这篇文章主要解决规模化使用MCP造成的两个问题：

1. 工具定义占据了大量上下文

2. 工具中间结果浪费大量tokens

这和我之前总结的那篇文章提到的Tool Search Tool和PTC很相似：**Introducing advanced tool use on the Claude Developer Platform **[www.anthropic.com](https://www.anthropic.com/engineering/advanced-tool-use)，只不过本文强调的的是MCP而不是tool。本文思路有相似之处，但也提供了不同视角，因此我将省略重复的部分，而着重新洞见。

# 新洞见

* 为所有连接着**MCP的工具做一个工具树**，连接的MCP server是文件夹，server下的每一个工具是一个文件。agent加载工具的方式就是探索这个树状文件系统，知道找到相应的文件，然后使用文件内的工具。

**个人思考：**这个和Tool Search Tool的本质区别在于，工具定义的渐进式加载到底是通过agentic search还是semantic search实现。semantic search实现可能会困难一些，特别是还需要依赖embedding模型。agentic search就比较依赖模型能力了。

* 在工具返回执行结果前，agent**先用代码做过滤以及格式转变，以节省上下文空间**。**把循环、条件分支合作务处理的逻辑放进代码里**，不要让模型花功夫去处理这个逻辑，这样能缩减TTFT时间（time to first token）。

* 隐私保护操作：把工具的中间结果中的敏感信息留在执行环境而不让模型知道。**将敏感数据tokenize为\[TOKEN\_NAME\]**，给模型处理完以后，再重新untokenize。要实现这一点，代码曾需要维护**一张token到原数据的映射表**。

**个人思考**：根据Anthropic以往的博客，魔法数字对于模型来说反而是干扰，如果能用tokenize后的id 1，2，3，反而比真实的id更利于模型理解。

* 状态保存和Skills：agent将**中间结果保存为文件**以追踪进度和继续工作。也可以**持久化agent写的代码**以便未来复用，当代码逐渐积累，就可以使用Skills将这些代码整合起来成为一个更高层能力的工具箱。要实现这一点，**沙箱环境**是必要的，代码执行的好处应与沙箱环境的实现成本间做工程取舍。

**个人思考**：持久化代码是我们真实工作中遇到的解决方案，但问题在于如何迭代这个代码，以及真正泛化agent的能力。本文也许就是答案。
